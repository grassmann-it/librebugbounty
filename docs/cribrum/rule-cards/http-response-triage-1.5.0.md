# HTTP-response triage: candidate 1.5.0

This candidate accompanies engine `cribrum-1.3.1`. It extends the existing four
registered detectors and observation codes. Core remains `2026.10.19`; policy,
handoff, worker proof and mail eligibility contracts retain their identities.
Installing code and selecting this candidate are separate operations.

## Query disclosure and request correspondence

A complete returned query in a bounded database diagnostic can establish
`internal_information_exposed/detailKind=query` without a request value. Error
and statement have separate raw spans. A value echoed only in later stack
arguments or a separate parameter list establishes no statement literal link.
SQLi still requires its existing structural evidence and remains suspected.

Synthetic positive: a real diagnostic element containing
`SQLSTATE[HY000]: General error: 1267 Illegal mix of collations` and
`Query: SELECT id FROM synthetic_records WHERE title = ?`.
The same text in a quoted HTML attribute, documentation, comment or template is
negative. A later `lookup(OPENBUG)` frame does not bind that value into `?`.
The separately accepted request-specific literal-query echo remains supported.

Base64 correspondence is one explicitly named, bounded transformation of a
once-parsed input value. It preserves parameter identity, raw attribute and quote
boundaries, and never asserts JavaScript execution. It adds no second URL or
entity decoding pass to that comparison.

## Frames, source locations and source windows

New delivered PHP method lists and Java paragraph frames require coherent calls,
source positions and local structure. New list forms require at least two actual
calls; UI counters, source lines and calls joined across containers do not qualify.
Module prefixes remain part of raw provenance rather than new vulnerabilities.
An independent valid stack on the same page remains visible.

PHP `/html/` locations are accepted only inside the already bounded error/frame
forms. Public relative Classic-ASP locations, including font-wrapped diagnostics,
are neutral runtime details. A relative filename alone grants no disclosure mail
component; existing absolute backend internals and independent queries remain
separate evidence. This is an intentional mapping correction for new results,
not a rewrite of historical database facts.

Actual PHP/JSP debug source windows require a bound diagnostic window, coherent
line positions and backend syntax. `code`/`samp`, a filename, tutorial, configuration
instruction or exception class in source alone is insufficient. Showing source
does not establish execution, credentials, inclusion or branch reachability.

## Runtime diagnostics and catalog context

Specific bounded backend diagnostics and approved structured error fields use the
existing `error_response` code with `runtimeDetails`. For example,
`__NEXT_DATA__.props.pageProps.error = "Failed to create resultsState"` with
embedded `statusCode=500` is preserved independently of the actual HTTP status.
It is not a stack and does not establish a static-props failure.

Approved concrete PHP, Java, .NET, Ruby/Lua, GraphQL, JCR, URLPattern and OData
diagnostic families require their bounded diagnostic carrier or an exact approved
error field. A source function returning an exception string, a catalog entry,
an ordinary JSON `message`, and unrelated neighboring blocks are negative.
For example, `Call to undefined function synthetic_lookup()` in a real error
element is a neutral runtime diagnostic; the same text assigned to `$message`
inside source is not an observed runtime event.

Structured carriers include selected `data.error` and `errors[].detail` paths,
bounded `meta.previous` chains, and explicit Nuxt root-error references. This is
not a general Nuxt deserializer or JSON repair engine. Nuxt parsing is limited to
64 KiB and 1,024 table entries; previous chains to depth four and 32 nodes. Actual
script attributes and exact closing tags are required. A malformed earlier
carrier must not suppress an independent later diagnostic. The single approved
malformed WordPress envelope preserves only a strictly valid terminal error
subobject while retaining `parser_error` and partial coverage for the outer JSON.

Runtime-only diagnostics and public ASP filenames remain neutral observations.
New disclosure components still require concrete internals. Private literals
remain context; an OData `$filter` parser error is not SQL injection and creates
no new injection claim. These mappings were explicitly confirmed by the user.

A statically delivered translation/diagnostic catalogue can use
`product_context` with `contextKind=diagnostic_catalog`, `catalogKind=i18n`, a
validated raw range and entry count. Its SQL/connection example strings are not
current backend events. An independent genuine error outside that range still
qualifies through its own existing evidence path. No script is executed.

## WAF and coverage

Explicit previously missing WAF rejection and actual hCaptcha/PoW access challenge
forms use the existing `coverage_limited` observation. Hosting branding is not a
WAF engine identity. Ordinary contact captchas, assets, status codes and isolated
worker/hash words are negative. Challenge alone grants no E7 hold; a new relevant
actual block follows the existing review/hold workflow without removing XSS proof.

Representation, parsing, depth and candidate budgets stay visible. Valid partial
evidence is retained; omitted work cannot certify strict purity. Unfinished
coverage alone creates no new mail hold.

## Validation and release boundaries

Public tests use synthetic values. Private originals remain in the ignored local
acceptance record, with capture/input hashes, byte/codepoint ranges and explicit
reading limits. Compare complete result, span, relation, claim, coverage and
Explain deltas against the secured engine1.2.0/candidate1.4.0 WIP baseline.
Shadow suggestions must equal Core suggestions from the same final engine.

Run detector/roundtrip tests, real Engine→SQLite→projection→selection→report-gen
tests, contracts and source/privacy checks before acceptance. Recipient contexts
must not copy private source values; original PoCs remain byte-identical.
No target request, scan, live reclassification, candidate activation or mail action
is implied by this release.
