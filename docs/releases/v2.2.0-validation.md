# Cribrum v2.2.0: technical and validation history

This record preserves the technical release-preparation notes and dated validation
results that accompanied Cribrum's development. Each result applies to the source
snapshot, runtime and scope named beside it. Historical statements about open
acceptance or unpublished status describe that preparation stage; they are not
current release status. Historical counts overlap and must not be added together.

See the [release announcement](../../.github/releases/v2.2.0.md) for the current
user-facing scope and limitations, and the [release procedure](../../.github/releases/README.md)
for publication checks. The evidence below does not establish general precision,
recall, throughput or universal site compatibility.

## Classifier and evidence

The classifier reads bounded, private HTTP/DOM observations from existing browser
runs, without additional target requests during normal processing. Versioned
rulepacks, evidence spans and rule explanations make its results inspectable.
SQLi/LFI/RFI are not automatically confirmed, and reflected input alone does not
establish XSS execution. Manual assessment remains authoritative.

The consolidated engine is **Cribrum 1.3.8**. The explicitly selectable
**behavior-triage 1.5.2 candidate pack** adds registered
SQL, file-include, reflection and context/disclosure/WAF detectors. It separates
SQL diagnostics from structural SQL suspicion, include errors from LFI/RFI
suspicion, and concrete internal details from generic error or product context.
Per-detector evaluation coverage records completed, limited, unavailable and
failed stages; a no-hit result alone does not certify complete coverage.
The consolidated detectors add bound query, stack/runtime, backend-source and
WAF observations while retaining neutral diagnostic catalogue context. Numeric
Oracle error-code validation prevents ordinary `ORA-` text from becoming a SQLi
suggestion.

The preceding engine 1.3.2 / candidate 1.5.1 correction recognizes concrete SQL
and runtime diagnostics even when the HTTP status is 200. It keeps observed errors
separate from suspected SQL injection and excludes documentation, translation catalogs,
generic product text and fully request-supplied SQL. Query evidence requires a
genuine statement in its response context: ordinary `Select`/`From` page prose,
HTML attribute lookalikes and unrelated JSON labels cannot supply it. Server-
generated SQL in hidden form fields and adjacent database diagnostics can be
reported with source-bound spans. A bounded JSON scan now respects UTF-8
character boundaries and still reports incomplete coverage. See the
[1.5.1 correction card](../../docs/cribrum/rule-cards/http-response-triage-1.5.1.md).

Engine 1.3.3 / candidate 1.5.2 additionally recognizes a bounded `DB ERR`
diagnostic followed by a concrete SQL statement, such as a multiline `SELECT`
query, even with HTTP 200 and an unclosed diagnostic container. The generic
wrapper supplies an observed database error with unknown vendor; it does not
establish SQL-injection suspicion or
confirmation. Request-supplied echoes and documentation/code contexts remain
excluded. See the
[1.5.2 correction card](../../docs/cribrum/rule-cards/http-response-triage-1.5.2.md).

Engine 1.3.4 adds a narrow **suspected SQL-injection hint** in the core suggestion
path. A qualified native MySQL SQLSTATE `42000` / error `1064` diagnostic can match
a long exact suffix of one unambiguous request value in its bounded
`near '…' at line N` excerpt. The hint explicitly retains partial-input and
missing-query uncertainty. It does not confirm SQLi, emit a structural candidate
fact or establish report eligibility. Candidate 1.5.2 and its strict structural
detector, explicit active mode and report policy remain unchanged. See the
[engine 1.3.4 rule card](../../docs/cribrum/rule-cards/mysql-syntax-suspicion-1.3.4.md).

Engine 1.3.5 extends that core hint to canonical native MySQL/MariaDB messages
without requiring a SQLSTATE prefix. Conflicting SQLSTATE wrappers and recognized
error-code prefixes remain excluded. An 80-byte ellipsis fragment may contain a
bounded SQL-keyword prefix after the long exact input suffix; it does not supply
a complete executed query. One local entity decoding inside the qualified near
fragment preserves original raw evidence spans. Unique input binding,
suspected certainty and partial-input/missing-query uncertainty remain required.
Candidate 1.5.2, explicit active mode and report qualification remain unchanged.
A separate core fallback can suggest suspicion from a qualified PDO SQLSTATE
`HY000` / general-error `20018` diagnostic, a complete disclosed query and an
exact long request value in an `IN` list attributed to supported ordered append-array
inputs. The diagnostic does not establish a database vendor or structural SQLi
evidence. This route likewise leaves strict candidate facts and report
qualification unchanged.
See the [engine 1.3.5 rule card](../../docs/cribrum/rule-cards/native-sql-suspicion-1.3.5.md).

Engine 1.3.6 adds a separate core suspicion path for a complete Phalcon PHQL
parser diagnostic. A byte-length-checked disclosed query, the adjacent closed
`parsePHQL()` trace and one distinctive request value at an unquoted `ORDER BY`
operand supply the relationship. Raw markup and original evidence spans are
preserved; PHQL namespaces and placeholders are handled within that grammar.
The hint explicitly states that ORM parsing does not prove native database
execution or a native SQL error. No typed SQL fact, active-mode change or SQLi
report eligibility is added. See the
[engine 1.3.6 rule card](../../docs/cribrum/rule-cards/phql-input-suspicion-1.3.6.md).

Engine 1.3.7 recognizes complete native MySQL/MariaDB diagnostics serialized
into isolated alert source frames and localized native Access expression
diagnostics with adjacent ASP source locations. Observed errors do not require
an input relationship; SQLi suspicion additionally needs a qualified unique
binding. One-pass serialization/entity comparisons retain exact raw spans.
These core helpers create no typed SQL facts and do not run in explicit active
mode. A separate PHP runtime correction recognizes supported native fatal
diagnostics when an abort leaves outer HTML open, and native result/resource
type warnings. Such database-result failures are observed runtime errors, not
SQLi evidence by themselves. A bounded native PostgreSQL negative-OFFSET
`query was:` carrier recognizes the disclosed query before a following trace;
reflected input in a separate request dump is not attributed to the query.
These corrections can add runtime and query-disclosure observations in active
mode; strict SQL structural/report requirements stay intact. The UI exposes
source-bound **SQL error** and **Database runtime error** causes consistently
in badges, filters and exports without promoting them to SQLi. See the
[engine 1.3.7 rule card](../../docs/cribrum/rule-cards/native-carriers-and-runtime-1.3.7.md).

Engine 1.3.8 corrects two shared causes behind repeated missed SQL hints.
Request values are now also decoded from the URL path, because a payload placed
in the path produced no request value at all and every SQL path returned before
inspecting the response. Path values stay out of the core context needles: a
reflected path alone must not qualify a page-wide error line. A new bounded
multi-line response carrier reads one complete statement that a debug page
echoes across several lines, where the previous carriers read a single line, an
attribute-free paragraph, or stopped at reflected markup. One suspicion helper
observes a request value that a disclosed statement retains verbatim and
unescaped inside its own quoting; the verbatim bytes of a quoting-carrying value
are themselves the evidence that the application did not escape it. The hint is
suspicion only and adds no typed fact, active-mode change or SQLi report
component. See the
[engine 1.3.8 rule card](../../docs/cribrum/rule-cards/disclosed-query-input-1.3.8.md).

The shipped core and private rulepacks remain the default. Candidate packs are
not selected by default; explicit selection starts in shadow mode. Active mode
requires separate opt-in and the complete detector/output selection. Installing
this source does not activate the candidate or reclassify the inventory. See the
[classifier guide](../../docs/cribrum/README.md) and
[activation procedure](../../docs/cribrum/activation.md).

## From findings to reports

Cases support multiple claims with immutable decision history. Shared badges show
each finding's certainty and link to its evidence in Review, inventory, workbasket,
detail and export preview. Saved views, statistics, UI filters and corresponding
CLIs use consistent selection for additional findings, new review context,
report kind and projection freshness.

Normal and focus Review show the findings selected for adoption before confirming
a case. Mouse, keyboard and swipe use the same choices; suspicion stays suspicion.
Deselecting a proposal records a rejection for that case and its exact evidence,
while the originating rule is queued for human review. The rule remains active.
The rule review queue is available from Review and Settings. Historical evidence
and manual decisions remain traceable.

A separate AI source-reading ledger binds an actual reading to retained source
bytes, request context and review policy. Atomic expiring reservations coordinate
parallel workers; reserving a source does not mark it reviewed. Case details show
open/pending/current/stale review, reviewer, time, outcome and summary. A changed
source/context needs its own reading. These receipts do not confirm a vulnerability
or change security claims, manual assessment, report eligibility or activation.

Versioned report projections bind qualified evidence to its source and current
PoC. Reports distinguish observation, suspicion and confirmation, retain qualified
additions in combined cases, and expose WAF review holds and missing/stale evidence.
Private HTTP artifacts are excluded unless explicitly selected. Candidate shadow
results do not become a current report basis. The report-handoff contract supports
the same interpretation in report-gen; eligibility does not send a report.

Local diagnostics explain stored and current classification without target
requests. Status and Settings expose packs and storage policy. Reclassification
preserves manual decisions and immutable historical results.
`app:cribrum:classify` offers a one-URL probe or offline response-file evaluation,
including JSON and explanations. Offline input also supports explicit candidate
comparisons; neither mode saves cases or jobs. `app:report:refresh` previews or
refreshes an explicit local selection without reclassifying or contacting targets.

## Workspace improvements

Backup listing, explicit retention previews, private-rulepack snapshots, storage
auditing and read-only upgrade permission checks support operations. Update information
separates version comparison from unverified installation origin.

Image Review keys and page-navigation combinations are configurable, with saved
bindings reflected in hints and keyboard help. Optional URL-paste intake uses
normal validation and starts disabled. Missing-image cases can explicitly queue
new screenshots; a readable current-PoC image resolves the current task without
altering historical evidence or assessments. Existing cases, manual assessments,
screenshots and reflected-XSS exports remain compatible through additive
migrations.

Intake keeps its **Already exists** receipt and existing-case link in global
history through refresh/reload, without adding personal progress. With
paste-to-submit disabled, pasting the exact full URL already in the input keeps
one copy and does not submit it. Different URLs and partial edits retain native
paste behavior; this does not canonicalize URLs or change exact-URL deduplication.

## Upgrade

Follow [the upgrade guide](../../README.md#upgrade-an-existing-workspace) and
[backup instructions](../../BACKUP.md). Upgrade the application and workers together;
keep the database, artifacts and any private rulepacks from the same workspace.
The upgrade adds the claim/observation ledger and immutable report-evidence and
projection schema. Review candidate activation separately; no historical case is
automatically enrolled into a fixed legacy XSS cohort.
An additional migration stores rule-review hints and immutable review events.
The source-reading ledger adds `Version20261026010000`, with separate receipt and
expiring-reservation tables; existing evidence and assessments remain separate.
PHP 8.4 is supported alongside the minimum PHP 8.3 runtime.
